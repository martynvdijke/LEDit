## Why

LEDit can already bias global rotation from display/skip counts (`handlers/adaptive_weights.go`, `handlers/analytics_weights_api.go`, shipped by `add-analytics-curation`), but there is no system-level notion of *intent*: changing the wall's mode means editing each device's `content_mode`/playlist, brightness windows, default theme and overlay strip by hand; event rules (`DisplayRule`, `handlers/eventrules.go`) are always evaluated even when they are wrong for the occasion; and the adaptive weights ignore the strongest engagement signals the wall actually emits — pins (`FeedController.Pin`), pauses (`FeedController.Pause`) and dwell time (`TrackDisplay`). Operators want one switch that puts the whole wall into "Workday", "Evening", "Party" or "Guest" mode atomically, and a curation loop that learns from what the household watches without ever breaking saved playlist order or leaving a wall blank.

## What Changes

- **System profiles (new)**: a named bundle that atomically applies a director playlist, a profile-tagged event-rule set, a brightness profile, a default theme, and an overlay strip. Profiles act as an inherited configuration layer: explicit device/group settings always win, and profile members apply only where configuration is inherited. Activation is validated first, committed in one transaction, logged (`from` → `to`, trigger, actor), and idempotently re-applied on startup. A seeded, non-deletable **Default** profile is the safe rollback target; deleting the active profile falls back to it. A missing/dangling member degrades to the existing fallback ladder (director playlist → global list → idle screensaver) with a warn log — a profile can never blank a wall.
- **Time-of-day profile scheduling (new)**: profiles carry `schedule_windows` reusing `ScheduleWindow`/`WindowMatches`/`ResolveScheduledPlaylist` from `handlers/schedule.go`; a `selection_mode` of `manual | scheduled` decides whether the wall is operator-pinned or follows the calendar, evaluated on the existing event-evaluator tick (`runEvaluator`, `handlers/eventrules.go:326`) — no new cron, ticker or scheduler. Highest matching window priority wins, ties by profile order, no match → Default profile.
- **Engagement-aware curation (extends `adaptive` ordering)**: `handlers/analytics.go` and `handlers/feed_control.go` capture canonical `type:id` signals — displays/dwell (`TrackDisplay`), skips (`RecordSkip`), pin holds (`FeedController.Pin`), pause holds and resume dwell (`Pause`/`Resume`). A bounded in-memory signal log and a pure decayed aggregation feed the existing `ComputeWeights` floor/exploration kernel with hold and dwell boosts, so pins/pauses/dwell bias rotation up and skips bias it down. Weights are recomputed on the existing 5-minute ticker plus the debounced skip trigger.
- **Explainability and opt-out**: `GET /api/analytics/weights` (`handlers/analytics_weights_api.go`) and the admin analytics page gain a per-source breakdown (raw signals, decayed score, skip penalty, hold/dwell boost, floor/exploration clamp, human-readable reasons) so operators can see *why* a source is weighted up or down. Signal-class toggles, per-source exclusions and the existing `ordering_mode` are admin-visible; disabling them reproduces the pre-change displays+skips behavior exactly.
- **Constraints preserved**: feed precedence stays `notification > incident > alarm > scene > pinned rule > rotation` (`handlers/websocket.go:1242-1304`); profiles are a configuration layer, never a feed tier, never pin, and never suppress notifications/incidents. Engagement-aware selection applies **only** to devices in effective `global` mode; devices on `playlist`/`scheduled` mode keep saved order (`handlers/websocket.go:811-815`), and `random`/`sequential` modes are byte-for-byte unchanged when `adaptive` is off. All tuning parameters are admin-visible; computation is deterministic and bounded.

## Capabilities

### New Capabilities
- `system-profiles`: Named profile bundles (director playlist, profile-tagged event rules, brightness, theme, overlay), inherited-config resolution and never-blank fallbacks, atomic validated activation with logging/rollback to a default profile, time-of-day profile scheduling on the existing evaluator, and the admin/API selection surface.
- `engagement-curation`: Canonical engagement signal capture (display, dwell, skip, pin, pause) with a bounded store, deterministic decayed weight computation with hold/dwell boosts layered on the existing adaptive kernel, global-mode-only biased rotation, explainability API/UI, and the opt-out/decay policy.

### Modified Capabilities
- None. `ordering_mode`/adaptive weighting is specified by the unarchived `add-analytics-curation` change (its `adaptive-ordering` spec is not yet in `openspec/specs/`), and `live-feed-control-room`, `device-management` and `ambience-modes` requirements are not contradicted: engagement-curation only adds signal inputs and explainability on top of the existing behavior, and profiles only add an inherited layer above existing device configuration. Interactions with the shipped feed tiering, scheduled-playlists and adaptive-ordering behavior are specified inside the two new capabilities rather than as deltas.

## Impact

- **New code**: `ent/schema/system_profile.go` and `ent/schema/profile_settings.go` (singleton: active profile, selection mode, last switch) + `go generate ./ent`; `handlers/profiles.go` (model, member resolution, atomic apply/rollback, schedule resolver, switch log); `handlers/profiles_admin.go` (admin CRUD/activate + API); `handlers/engagement.go` (bounded signal log + pure aggregation/explainability); `web/templates/admin/profiles.html`; analytics weight-breakdown UI/TS.
- **Modified code**: `handlers/adaptive_weights.go` (decayed signals, hold/dwell boosts, reasons, recompute); `handlers/analytics.go` (canonical signal recording); `handlers/analytics_weights_api.go` (breakdown fields); `handlers/feed_control.go` (`CurrentKey` tracking, pin/pause/resume signals); `handlers/feed_render.go` (`nextPushIndex` adaptive guard) and `handlers/websocket.go` (`composeDeviceSources` profile playlist layer; `serveFeed` real weighted selection in global mode); `handlers/output_runner.go` (global-mode-only adaptive rotation); `handlers/brightness.go` and `handlers/theme.go` (inherited profile layer / default-theme swap); `handlers/eventrules.go` (only profile-tagged rules active under the active profile); `ent/schema/displayrule.go` (`profile_id`); `handlers/server.go` (routes); `handlers/handlers.go` (nav/forms).
- **API surface**: admin CRUD/activate at `/admin/profiles`; `GET /api/profiles` and `POST /api/profiles/:id/activate` (session or bearer, admin for mutation); `GET /api/profiles/resolve?at=RFC3339` debug; `GET /api/analytics/weights` extended with per-source signal breakdown and reasons. No device-protocol change.
- **Dependencies**: none new — stdlib time/math plus existing Ent/Gin; scheduling and evaluation reuse existing code paths.
- **Risk**: profile switches thrash if windows overlap (deterministic priority + boundary change detection); engagement feedback loops (existing epsilon/floor plus capped hold/dwell boosts and per-source exclusion); noisy pause signals (bounded hold weight, only attributed when a source is on-screen); profile members becoming dangling at runtime (fallback ladder + warn log, never blank); profile-tagged rules silently disabling alarms-like rules (untagged rules always evaluate; only explicitly tagged rules switch).
