## Why

Home Assistant can barely drive the wall and event rules can barely act on it. HA MQTT discovery (`publishHADiscoveryForDevice`, `handlers/ha_discovery.go:23`) exposes only `online`, `brightness` (a `number`), `paused`, `next`, `firmware`, `transport`, plus three global entities — there is no light, no way to choose content, no way to render a message — and discovery plus entity state are (re)published only on MQTT connect, device save, and delete (explicit limitation at `handlers/ha_discovery.go:10`), so HA holds stale values between those moments. Inbound MQTT (`handlePerDeviceCommand`, `handlers/mqtt.go:162`) accepts next/pause/brightness but nothing to select content or push a message. Rule then-actions (`ThenAction`, `handlers/ruleactions.go:15`) support only `none|scene|notification|webhook`, so a condition cannot dim a panel, pin a source, switch a playlist, publish MQTT, or make a signed outbound call. This change makes the wall a two-way Home Assistant citizen and turns event rules into a general actuation surface — through the same feed controllers and brightness resolution that already govern the wall.

## What Changes

- **Home Assistant control entities**: add per-device `light` (brightness, on/off semantics, reusing `ledit/device/<id>/brightness/state` + `/set`), `select` (content picker with stable option values `source:<type>:<id>`, `playlist:<id>`, `scene:<id>`), and `text` (render an arbitrary message) discovery configs, all additive to the existing six per-device and three global entity configs, which stay byte-compatible.
- **State republish on change**: keep the existing connect/device-save republish and add retained HA state publishes on entity changes (brightness, pause/resume, current source, device liveness, select applied, message fired/expired) and config republish when playlist/scene/device content changes alter select options; all gated by `outbound_settings.ha_discovery_enabled` and independent of `mqtt_publish_enabled` so HA entities stay coherent.
- **Inbound MQTT actuation**: subscribe per-device `ledit/device/+/select/set` and `ledit/device/+/message/set` in `MQTTController.subscribeAll` (`handlers/mqtt.go:111`); every per-device command resolves the target device's registered `FeedController` (`getDeviceFeed`, `handlers/feed_control.go:52`) so pause/resume/next/select/brightness land on the same controller; unknown or offline devices are a logged no-op with no state mutation. Existing control, display, brightness, paused, and next topics are unchanged.
- **Rule then-action expansion**: extend `ThenAction`/`ParseThenAction`/`validateThenAction`/`executeThenAction` (`handlers/ruleactions.go`) with `brightness` (device or all, level 0–100), `source` (pin), `playlist` (switch), `mqtt` (publish topic/payload), and `http` (signed outbound call reusing the HMAC convention at `handlers/outbound.go:368`); stored rule JSON and the four existing kinds keep working unchanged, and the admin form (`web/templates/admin/eventrule_form.html`) gains controls for the new kinds.
- **Shared actuation paths**: MQTT, HA entities, and rule actions call shared helpers (`handlers/actuation.go`) that write `brightness_override` and notify live `FeedController`s, use `FeedController.Pin` for source selection with `pinAll`/`unpinAll` semantics, use `PreviewScene` for scene selection (`handlers/scenes.go:701`), and use the notification path for messages — precedence stays notifications > pinned rule > rotation (`handlers/feed_control.go`).
- No **BREAKING** changes: no entity topic or unique ID is renamed, no existing MQTT topic changes meaning, no existing then-action config stops parsing, and no new required settings.

## Capabilities

### New Capabilities
- `homeassistant-control-entities`: The additive HA MQTT discovery entity surface (light, select, text), their command/state topics, state republish behavior on change, select-option refresh triggers, and compatibility/cleanup rules for the existing entities.
- `mqtt-actuation`: The inbound per-device MQTT command surface (select, message; brightness/paused/next documented as-is), command grammar and validation, offline-safe no-op routing to the target device's feed controller, and retained state feedback.
- `rule-action-expansion`: The backward-compatible expansion of event-rule then-actions with brightness, source pin, playlist switch, MQTT publish, and signed outbound HTTP kinds, including validation, admin configuration, and failure-isolation behavior.

### Modified Capabilities
- None — no capability under `openspec/specs/` currently specifies HA discovery, MQTT command handling, or rule then-actions: `mqtt-control` (`openspec/changes/push-to-display/`) and `event-driven-switching` (`openspec/changes/add-event-driven-switching/`) exist only as unarchived deltas, so nothing tracked is contradicted. The behavior is specified as ADDED requirements in the new capabilities, mirroring how `add-fleet-ops` kept its interactions inside new capabilities.

## Impact

- **Modified server code**: `handlers/ha_discovery.go` (new light/select/text configs, republish triggers, cleanup), `handlers/mqtt.go` (new subscriptions + per-device command routing), `handlers/feed_control.go` (live brightness hint and select/message application on a controller), `handlers/ruleactions.go` (new kinds parse/validate/execute), `handlers/eventrules.go` (form parse/build/prepopulate), `handlers/outbound.go` (HA state sink / reusable signed delivery helper), `handlers/handlers.go` and `handlers/scene_admin.go` (republish hooks on content changes), `handlers/websocket.go` (notification target filtering; extended reschedule refresh for content-mode switches).
- **New server code**: `handlers/actuation.go` (shared brightness/select/message helpers used by MQTT, HA, and rule actions), optional `handlers/ruleactions_http.go` (async signed outbound dispatch).
- **Admin UI**: `web/templates/admin/eventrule_form.html` (new then-kind fields); no new admin routes required.
- **API surface**: no new HTTP routes; new MQTT topics `ledit/device/<id>/select/set`, `ledit/device/<id>/select/state`, `ledit/device/<id>/message/set`, `ledit/device/<id>/message/state`, and the three new HA discovery config topics.
- **Dependencies**: none new — reuses the paho MQTT client (`handlers/mqtt.go`), the hand-rolled discovery publisher (`publishDiscovery`, `handlers/ha_discovery.go:172`), the existing `GlobalBus`/sink registration, and the outbound HMAC code.
- **Risk**: MQTT broker ACLs remain the only authority for commands (documented, no new auth layer); select options are dynamic and must be republished to avoid stale HA pickers; rule actions persist device config (brightness override, playlist), so automation can overwrite admin edits (last-writer-wins, surfaced in state topics); retained message topics are bounded per device and cleared on expiry/delete.
