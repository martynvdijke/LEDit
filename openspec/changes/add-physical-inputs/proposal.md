## Why

The device↔server direction of protocol v2 carries exactly three things today: button `{"action":"next"|"pause"|"hold"}` control messages (`handlers/websocket.go:1140-1154`) and an opt-in `{"type":"spectrum","bins":[...]}` tap (`handlers/websocket.go:1129-1139`). Everything physical at the panel — a tag tapped on an NFC/RFID reader, a rotary encoder turned, a person in front of a PIR/mmWave sensor, the room getting darker — is invisible to the server, so "tap to start dinner mode", panel-local presence greetings, and device-measured auto-brightness cannot be built. The only local controls that exist are hardwired next/pause GPIO (`LEDIT_BTN_NEXT_PIN`/`LEDIT_BTN_PAUSE_PIN`, `device/ledit_device/buttons.py:60-61`), and auto-brightness can only read a Home Assistant lux entity (`FetchSensorLux`, `handlers/brightness.go:280`). This change turns the panel's local hardware into a first-class input source that feeds the existing scene, playlist, feed-controller, brightness, and greeting machinery instead of growing a one-off path per sensor.

## What Changes

- **Input-event protocol (additive v2)**: the v2 welcome (`handlers/websocket.go:761-771`) gains an `inputs` capability and the server accepts one new device→server message, `{"type":"input","event":"press|rotate|tap|presence|lux","source":"button:next|button:pause|encoder|nfc|pir|mmwave|lux","value":<int|string|number>,"ts":<unix>}`. The handshake, frame keys, and legacy `{"action":...}` messages are unchanged; v1 connections and servers that do not advertise `inputs` behave exactly as today.
- **Device input modules (all optional)**: new `device/ledit_device/inputs.py` event hub plus per-source helpers for NFC/RFID (`nfc.py`), rotary encoder (`rotary.py`), and presence/lux (`sensors.py`). Each source starts best-effort and logs once then no-ops when the pin or library is absent, mirroring `ButtonHandler.start()` (`device/ledit_device/buttons.py:187-221`). Existing GPIO buttons are extended to route through the hub rather than duplicated.
- **Encoder/button defaults**: a short encoder rotation emits `rotate` (+1/−1); the encoder switch emits `press`. Built-in server defaults are rotate → next/previous, encoder press → brightness cycle, while `button:next`/`button:pause` keep their current next/pause/hold meaning; every default is overridable by an admin binding and the device-side behavior is unchanged when the server does not advertise `inputs`.
- **Server-side input bindings**: a new `InputBinding` entity and admin CRUD surface mapping (device, source, event, optional value/tag) → action, evaluated in order with device-specific bindings winning over global ones. Action kinds are `scene`, `playlist`, `feed`, `brightness`, `rule`, and `greeting`; unknown or unmatched events are debug-logged and dropped.
- **Convergence on existing machinery**: scene actions go through `PreviewScene`/`resolveSceneSource` (`handlers/scenes.go:701,764`); playlist actions update the device's `playlist_id`/`content_mode` and request a live source reload through the existing reschedule plumbing (`handlers/websocket.go:888-919,1215-1217`); feed actions call the per-device or global `FeedController` (`handlers/feed_control.go:25,75-111`) with a `Prev` symmetric to `Next`; brightness actions persist `brightness_override` (`ent/schema/device_settings.go:46`) and update the live override tier; rule actions call `executeThenAction` (`handlers/ruleactions.go:77`); greeting actions reuse greeting-rule template/quiet-hours/cooldown and `AddNotification` (`handlers/greetings.go:110-197`). No parallel action path is introduced.
- **NFC/RFID tap → scene or playlist**: a `tap` event carries the tag id as its value; a binding matches the tag and runs the scene/playlist action ("tap to start dinner mode"). Taps with no matching binding, or repeated within a short dedupe window on the same device, are ignored.
- **Presence + lux feed existing pipelines**: presence edges (`presence` events from PIR/mmWave) are eligible for bindings and greeting actions; device lux readings land in a bounded per-device in-memory cache consulted by the existing brightness resolution (`ResolveEffectiveBrightnessWithScene`, `handlers/brightness.go:184`) as a sensor source beside the HA fetch, with the same staleness rule and unchanged precedence (override > alarm > scene > sensor > schedule > 100).
- **Optional HA/MQTT exposure**: input events are published through the existing `PublishOutbound` helper (`handlers/mqtt.go:393`) on `ledit/device/<id>/input/...` and HA discovery gains an input event entity (`handlers/ha_discovery.go`); both are no-ops when MQTT/HA discovery is disabled.
- **Auth and degradation constraints**: input events are accepted only on the token-authenticated device WebSocket (`HandleDeviceWS`, `handlers/websocket.go:730`), only when v2 plus `inputs` is negotiated, and are rate-limited per connection; no new inbound listener is opened on the device and no token or secret ever appears in an event payload or MQTT topic.

## Capabilities

### New Capabilities
- `physical-inputs`: Device-side acquisition and transport of local hardware input events — button, NFC/RFID, rotary encoder, presence, and ambient lux sources; the additive `{"type":"input",...}` v2 message and `inputs` capability negotiation; encoder/button defaults; per-source graceful degradation; and event validation, dedupe, and rate discipline.
- `input-bindings`: Server-side admin-configurable mapping from input events to existing actions (scene, playlist, feed next/previous/pause/resume, brightness, event rule, greeting), the convergence rules onto existing feed/scene/brightness/greeting code paths, local lux and presence integration with the existing brightness and greeting pipelines, optional MQTT/HA event exposure, and the admin surface.

### Modified Capabilities
- None — all requirements are ADDED under the two new capabilities. `device-client`, `device-management`, and `device-streaming` requirements are unchanged (the client still connects with a token, renders frames, and configures the matrix; input sources are additive), and `device-protocol-v2` exists only as an unarchived change under `openspec/changes/add-device-protocol-v2/`, so there is no archived spec whose requirements change. The new capability explicitly preserves every existing v2 behavior it builds on.

## Impact

- **New server code**: `ent/schema/input_binding.go` (+ `go generate ./ent`), `handlers/input_bindings.go` (event validation, binding lookup, dispatcher), `handlers/input_actions.go` or equivalent action executors, `web/templates/admin/input_bindings.html` and a device-page include.
- **Modified server code**: `handlers/websocket.go` (welcome `inputs` capability, `{"type":"input",...}` ingestion in the read loop at `handlers/websocket.go:1100-1155`, lux/override consultation in `bFn`, source-reload flag on the feed), `handlers/brightness.go` (local lux source beside `FetchSensorLux`), `handlers/greetings.go` (input-driven greeting firing through the same cooldown/quiet-hours/template code), `handlers/feed_control.go` (`Prev` and a reload request mirroring `Next`), `handlers/output_runner.go` (lux/override parity for non-WebSocket transports), `handlers/mqtt.go` and `handlers/ha_discovery.go` (input event publication/discovery entries), `handlers/server.go` (admin routes), `handlers/handlers.go` (device detail surface).
- **New device code**: `device/ledit_device/inputs.py` (event model, hub, sender, capability gating, dedupe/throttle), `device/ledit_device/nfc.py`, `device/ledit_device/rotary.py`, `device/ledit_device/sensors.py`; modified `buttons.py`, `client.py`, `config.py`, `__main__.py`.
- **Device dependencies**: optional extras (`nfc` for a PN532/`nfcpy`-style reader, `smbus2`/`gpiod` for rotary/lux) so the default install and all hardware-absent paths keep working exactly as today; no new required dependency.
- **API surface**: admin session routes for binding CRUD plus optional device-facing routes off the existing WebSocket; no new unauthenticated HTTP endpoint.
- **Docs**: `README.md` "Push-to-Display"/device section and `device/README.md` gain env-var tables, event vocabulary, binding examples, and hardware wiring examples (reader/encoder/PIR/lux bus and GPIO pinout, pull-ups, I2C addresses).
- **Risk**: noisy sensors or bouncing GPIO could flood the WS and retrigger actions; duplicate NFC reads or presence flapping could retrigger scenes; a bad binding could fight alarms/incidents; local lux could disagree with HA. Mitigations: bounded event size and per-connection rate limit, device-side debounce/dedupe, server-side tag/dedupe window, binding actions always routed through the existing precedence-aware tiers, and explicit staleness + precedence for lux.
